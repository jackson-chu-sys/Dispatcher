# 01 · 需求

**状态：已定稿 v2（2026-11-11）** ｜ 依据神朱对 Q1–Q11 的回答整理

> v1 为草案骨架；v2 把 11 个待确认项全部落定，并据回答**修正了范围重心**：不是"排班系统"，
> 而是"**乘客能叫到车、司机能一键更新、调度能看见车在哪**"的实时调度台。

---

## 1. 要解决的问题（原话整理）

现状：全靠微信群协调，没有任何系统。

- 路上车多，乘客**坐不上车，也不知道车在哪**；
- 乘客状态（是否上车）靠司机在微信群里喊，前台再人工更新；
- 结论：需要一个**乘客端极简叫车入口** + **司机端一键上报**，让状态自己流动，而不是靠人转述。

**优先级（P0 → P1）**：位置可见 & 叫车闭环 > 班次排班 > 统计报表。

## 2. 范围

**做**：车辆/司机/线路/站点台账、班次、到站上报、实时位置、乘客叫车、派单（人工指派）。
**不做**（神朱确认）：乘客端 App、在线支付、跨城长途、维修保养工单、自动排班算法、智能就近派单、电量/续航纳入调度。

## 3. 角色与入口

| 角色 | 入口 | 能做什么 |
|---|---|---|
| 乘客 | H5 `/rider` | 输入起点/终点（固定站点）→ 叫车 → 看到接单车在哪 → 送达结束 |
| 司机 | H5 `/driver` | 看今日班次 → 发车 / **一键到站**（位置来源）→ 接单 → 标记"已接到乘客" → 送达 |
| 调度员 | Web `/dispatcher` | 地图看全部车辆 → 今日班次 → 指派/取消叫车 → 事件日志 |
| 管理员 | 同上（Demo 未分权） | 台账维护（Demo 用种子数据，界面待补） |

## 4. 关键业务流程

### 4.1 乘客叫车（P0）
1. 乘客在地图/列表里选**起点站**与**终点站**（固定线路站点，不让乘客自由输入地址）。
2. 提交叫车 → 状态 `waiting`，调度端与所有司机端立刻可见。
3. 司机接单 → `accepted`，乘客端显示接单车牌、司机、车辆当前位置。
4. 司机点"已接到乘客" → `boarded`；点"送达完成" → `done`。
5. 任一环节可取消 → `cancelled`；每次状态变更写事件日志（谁、何时、从什么到什么）。

### 4.2 位置更新（P0，到站触发）
- **不做连续 GPS 上报**（神朱定 Q6：先用最简单的，到站触发）。
- 司机点站点按钮 = 上报"这辆车现在在这个站"，附带服务器时间戳。
- 调度端/乘客端 3 秒轮询拿最新位置，显示"X 站 · N 秒前上报"。
- 好处：省流量、省电、绕开手机后台 GPS 不可靠的问题（H5 在 iOS/微信里长期定位本来就不稳）。

### 4.3 班次
- 线路固定（线路与站点由管理员/调度维护，支持在地图上生成 —— Demo 先用种子坐标，地图编辑待补）。
- 每个班次 = 发车时间 + 线路 + 车辆 + 司机；`Shift` 是计划，`Trip` 是当天实际运行实例。

## 5. 约束与规模

| 项 | 结论 |
|---|---|
| 部署 | 绿联 NAS 内 Docker（容器内 8010，宿主映射 8000；8010 宿主未开放） |
| 规模 | 暂定几十辆车与司机，先小规模；**不要数据库服务**，用单文件库，后期再改造 |
| 司机端形态 | **小程序最理想**，但上架流程若麻烦就先 H5 —— 见 `04-decisions.md` D7 |
| 地图 | 腾讯位置服务（神朱定 Q10） |
| 位置延迟容忍 | 5 秒（Q11），当前轮询 3 秒满足 |
| 电动车电量 | 不纳入调度，司机自己掌握（Q4） |

## 6. 验收标准（阶段 1）

1. 乘客从打开页面到叫车成功 ≤ 3 次点击。
2. 司机点"到站"后，调度端与乘客端 5 秒内看到新位置。
3. 叫车全链路（叫车→接单→上车→送达）状态留痕，能在事件日志里查到。
4. 排班冲突（同车/同司机同时间）被系统拦下。
5. 一台 NAS 上 `docker compose up -d` 即可运行，重启后数据不丢。
