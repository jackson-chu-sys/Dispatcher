# 01 · 需求

**状态：草稿** ｜ 最后更新：2026-11-10

已确认的项目定位（2026-11-10 神朱选定）：**班车 / 电动车调度系统** —— 车辆、司机、线路、班次、实时位置、派单。
下面是据此推导的第一版骨架。**除"项目定位"外，其余内容均为待确认的草案**，用 `【待确认】` 标注。

---

## 1. 目标与边界

**要解决的痛点（待确认）**：`【待确认 Q1】` 目前调度靠什么？（微信群喊话 / 电话 / Excel 排班 / 无系统）
最可能的三类问题——排班靠人排、临时用车靠电话找人、车在哪不知道。请神朱确认优先级。

**范围内**：车辆与司机台账、线路与站点、班次排班、派单、实时位置查看。
**范围外（明确不做）**：`【待确认 Q2】` 建议先不做：乘客端 App、在线支付、跨城长途、维修保养工单。

## 2. 角色

| 角色 | 典型人 | 主要动作 |
|---|---|---|
| 调度员 | 车队值班 | 看车辆实时位置、排班、临时派单、改派、处理异常 |
| 司机 | 班车/电动车驾驶员 | 收派单、上报位置与状态（到场/满员/故障）、完成确认 |
| 管理员 | 车队负责人 | 车辆/司机/线路/班次维护，查看统计 |
| 乘客 | 乘车员工 | `【待确认 Q3】` 是否需要独立的查询入口（看车到哪/查班次），还是只用大屏或微信通知 |

## 3. 核心对象（数据模型的第一版草案）

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `Vehicle` 车辆 | 车牌、类型（班车大巴/电动车/轿车）、座位数、状态（空闲/在途/维修）、当前司机 | 电动车需考虑电量与续航 `【待确认 Q4】` |
| `Driver` 司机 | 姓名、电话、准驾车型、可服务车辆、在岗状态 | 一名司机 vs 一辆车的绑定关系待定 |
| `Route` 线路 | 名称、方向（去/回）、站点序列（含经纬度）、里程、预计时长 | `【待确认 Q5】` 线路是否固定，还是每次行程临时生成 |
| `Stop` 站点 | 名称、经纬度、允许停靠时间窗 | |
| `Shift` 班次 | 线路、发车时间、车辆、司机、座位容量、已乘车人数 | 周期班次（每周几）vs 单次班次 |
| `Trip` 行程实例 | 由班次生成的实际一次运行，含实际发车/到站时间、延误 | 班次是计划，行程是实际发生 |
| `DispatchOrder` 派单 | 需求来源、用车人、起终点、期望时间、指派车辆/司机、状态流转 | 临时用车走派单；班车按班次走 |
| `PositionReport` 位置上报 | 车辆、经纬度、时间、速度、电量/油量 | 高频写入，只保留近期明细 |

## 4. 功能范围

### 4.1 阶段 1 · 最小可用（建议）
1. 车辆 / 司机 / 线路 / 站点 / 班次的基础台账（增删改查）。
2. 排班：按周模板生成班次，冲突检测（同车同司机同时间重复）。
3. 实时位置：司机端上报 → 调度端地图上看车。`【待确认 Q6】` 上报方式与频率。
4. 临时派单：调度员建单 → 指派 → 司机接单 / 完成 → 状态可追溯。

### 4.2 阶段 2· 增强
- 大屏看板（在线车辆、准点率、今日班次完成率）。
- 微信 / 短信通知（发车提醒、派单提醒、延误通知）。
- 到站预测（按历史行程估算 ETA）。
- 司机端离线容错（弱网缓存后补传）。

### 4.3 明确推迟
- 自动排班算法（先人工排 + 冲突检测）。
- 智能派单（就近/最空闲），先人工指派。

## 5. 现状与约束

- 部署环境：绿联 NAS（Docker），单机即可，无需集群。`【待确认 Q7】`
- 用户规模：`【待确认 Q8】` 车辆数 / 司机数 / 每日班次量级（决定是否需要 Postgres + PostGIS）。
- 司机手机端形态：`【待确认 Q9】` 微信小程序 / H5 网页 / 独立 App（App 成本最高，建议 H5 或小程序）。
- 地图与定位服务：`【待确认 Q10】` 国内可用性优先（高德 / 腾讯地图），海外环境另议。
- 移动端上报位置的硬件：司机手机 GPS 还是车载设备？

## 6. 验收标准（阶段 1）

- 调度员能在一次页面操作内完成：建线路 → 排班次 → 指派车辆司机。
- 司机点一下就能上报位置，调度端 5 秒内可见。`【待确认 Q11】` 5 秒是否够。
- 临时派单从建单到完成，状态变化全程留痕可查。
- 排班冲突 100% 被系统拦下（不靠人眼）。
